## 1. Назначение проекта

ZanKomek AI — юридический AI-помощник по законодательству Республики Казахстан. Пользователь описывает ситуацию на естественном языке и выбирает область права и тип субъекта (физическое лицо, ИП, ТОО); система возвращает структурированный правовой анализ: правовую оценку, применимые нормы, анализ рисков, рекомендуемые действия, перечень документов и список источников.

Центральное продуктовое требование — **достоверность источника**. Система обязана отличать:

- норму, подтверждённую текстом официального акта;
- норму, о которой рассуждает языковая модель, но которая не подтверждена;
- официальное разъяснение, не заменяющее текст закона;
- рекомендацию или шаблон.

Инженерное следствие этого требования — вся архитектура подтверждения вынесена на сервер и отделена от качества поиска.

## 2. Архитектура

### 2.1 Полный конвейер запроса

```
User input (legalArea, userType, description [, DOCX])
  │
  ├─▶ retrieveLegalContext()                    lib/retrieve-legal-context.ts
  │     ├─ query embedding (OpenAI)             lib/embed-legal-query.ts
  │     ├─ semantic candidate pool (50)         lib/search-legal-embedding-records.ts
  │     ├─ hybrid reranking                     lib/rerank-legal-candidates.ts
  │     ├─ final Top-K (5)                      LEGAL_RETRIEVAL_TOP_K
  │     ├─ definition expansion                 findDefinitionRecord()
  │     └─ token bounding (2000 / 8000)         boundRetrievalContext()
  │
  ├─▶ legal source search (Tavily)              lib/run-legal-source-search.ts
  │     └─ relevance enrichment                 lib/enrich-search-results.ts
  │
  ├─▶ buildLegalAnalysisPrompt()                lib/legal-prompt.ts
  ├─▶ LLM analysis (OpenAI Responses)           lib/openai-client.ts
  ├─▶ parseAnalysisResult()                     lib/parse-analysis-result.ts
  │
  ├─▶ retrySearchForModelActs()                 повторный поиск по актам модели
  ├─▶ Adilet / content verification             lib/fetch-official-source-content.ts
  │                                             lib/parse-adilet-articles.ts
  ├─▶ enrichAnalysisWithSearch()                lib/confirm-sources-with-search.ts
  │     ├─ confirmLegalSourceWithSearch()       статус источников
  │     ├─ linkApplicableLawsToSources()        source_confirmed / source_article /
  │     │                                       нормализация verification_status
  │     ├─ computeVerifiedBySearch()
  │     └─ computeLegalInformationStatusFromSearch()
  │
  └─▶ final API response (JSON)                 app/api/analyze/route.ts
```

Retrieval подключён как отдельная зависимость маршрута (`AnalyzeHandlerDependencies.retrieveLegalContext`) и деградирует мягко: его отказ логируется и не прерывает запрос — анализ продолжается без семантического контекста.

### 2.2 Архитектурный инвариант

> **Semantic relevance, retrieval и reranking не могут устанавливать юридическое подтверждение источника.**

Практическое выражение инварианта в коде:

| Слой | Что может | Что не может |
|---|---|---|
| Retrieval / reranking | давать `retrieval_score`, порядок кандидатов, контекст для промпта | читать или записывать `source_confirmed`, `search_confirmed`, `content_checked`, `verification_status` |
| Языковая модель | предлагать норму и статус-подсказку | подтверждать источник |
| Verification pipeline (сервер) | устанавливать `source_confirmed`, `source_article`, итоговый `verification_status` | — |

Тип `LegalEmbeddingSearchResult` не содержит ни одного поля верификации. Модуль `rerank-legal-candidates.ts` — чистая функция без ввода-вывода; во всём файле нет ни одного обращения к полям подтверждения. Инвариант закреплён тестами `app/api/analyze/rag-integration.test.ts` (в частности `a retrieval_score of 1 cannot confirm a source` и `a retrieved article_number cannot create a confirmed source_article`).

**Почему 1999 статей дают 2002 записи.** Постатейный чанкинг сохраняет статью целиком, пока она укладывается в лимит токенов. Три длинные статьи не уложились и были разбиты надвое — 6 записей с `chunk_total > 1`. Отсюда 1999 − 3 + 6 = **2002**. Все прочие записи соответствуют статье один к одному.

Сборка артефакта: `npm run build:legal-embeddings` (`scripts/build-legal-embeddings.ts`). Это офлайн-этап, при обычном запуске приложения он не выполняется.

## 5. Semantic retrieval

Поиск — точное вычисление косинусной близости по всем записям, без приближённого индекса (ANN). При 2002 записях это оправдано: полный проход занимает единицы миллисекунд и даёт точный, а не приближённый результат.

| Параметр | Значение |
|---|---|
| Метрика | косинусная близость (`lib/cosine-similarity.ts`) |
| Кандидатный пул | **50** (`LEGAL_RETRIEVAL_CANDIDATE_POOL`) |
| Финальный Top-K | **5** (`LEGAL_RETRIEVAL_TOP_K`) |
| Бюджет одного чанка | **2000** токенов (`LEGAL_RETRIEVAL_MAX_CHUNK_TOKENS`) |
| Бюджет всего контекста | **8000** токенов (`LEGAL_RETRIEVAL_MAX_CONTEXT_TOKENS`) |
| Путь к артефакту | переменная окружения `LEGAL_EMBEDDING_ARTIFACT_PATH` |

Свойства реализации:

- **Ранжирование стабильно**: при равных оценках порядок определяется исходным индексом.
- **Обрезка по бюджету не портит корпус**: `boundRetrievalContext` возвращает копии, записи артефакта остаются с полным текстом. Закреплено тестом `bounding the prompt context leaves the artifact records untouched`.
- **Обрезка идёт по границам слов**: длина префикса подбирается двоичным поиском по фактическому числу токенов, а не отсечением по произвольному смещению.
- **Definition expansion.** Семантическое ранжирование находит применимую норму, но не её легальное определение. Поэтому действует короткий декларативный список: если в Top-K попала норма закона о защите прав потребителей с понятием «технически сложн…», а определяющая статья 1 отсутствует — она добавляется детерминированно, из уже загруженных записей и с уже вычисленным эмбеддингом запроса, без дополнительного чтения и без сетевого вызова. Сейчас в списке **одно правило**; это не движок правовых рассуждений.
- **Неконфигурированное состояние — штатное**: без `LEGAL_EMBEDDING_ARTIFACT_PATH` retrieval возвращает пустой контекст и не создаёт OpenAI-клиент.

## 6. Hybrid reranking

Гибридное переранжирование добавляет к семантической оценке два лексических сигнала.

```
hybridScore = retrieval_score
            + TITLE_OVERLAP_ALPHA × titleOverlap(query, article_title)
            + (act_id === predictedActId ? PREDICTED_ACT_BOOST : 0)
```

| Параметр | Значение |
|---|---|
| `TITLE_OVERLAP_ALPHA` | **0.15** |
| `PREDICTED_ACT_BOOST` | **0.05** |
| Минимальная длина основы | 3 символа (`MIN_STEM_LENGTH`) |

**Русская нормализация.** Лёгкое детерминированное отсечение одного словоизменительного окончания по общему списку окончаний существительных и прилагательных. Это **не** Snowball, **не** Porter и **не** морфологический анализатор: нет словаря, нет частей речи, нет исключений. Окончание отсекается только если остаётся основа приемлемой длины, поэтому короткие слова («срок», «три») остаются нетронутыми. Соответствие эталону проверено на замороженном наборе: 51 словоформа, обработанная в Colab через `nltk.stem.snowball.SnowballStemmer("russian")`, воспроизводится точно. Это паритет на этих 51 случаях и не более того.

**Пересечение заголовков** нормируется по заголовку статьи, а не по запросу: короткий точный заголовок не проигрывает длинному. Отсутствие `article_title` даёт 0, а не ошибку.

**Предсказанный акт** — акт лучшего семантического кандидата; он даёт только бонус. Кандидаты остальных актов остаются в пуле и могут выиграть. **Фильтрации нет ни на одном шаге**: на выходе ровно те же кандидаты, что на входе, в другом порядке.

Переранжирование видит весь пул из 50, а промпт по-прежнему получает Top-5 — обрезка происходит после переупорядочивания.

## 7. Verification architecture

### 7.1 Два разных статуса с одинаковым именем

| Поле | Кто устанавливает | Семантика |
|---|---|---|
| `LegalSource.verification_status` | `verifyLegalSourceUrl()` по домену URL | официальность **домена**, не подтверждение нормы |
| `ApplicableLaw.verification_status` | модель предлагает → сервер нормализует | итоговый статус нормы |
| `ApplicableLaw.source_confirmed` | только `linkApplicableLawsToSources()` | **authoritative** признак подтверждения |

Список официальных доменов (7): `adilet.zan.kz`, `zan.gov.kz`, `gov.kz`, `sud.gov.kz`, `office.sud.kz`, `kgd.gov.kz`, `nationalbank.kz`.

### 7.2 Условие подтверждения

Норма считается подтверждённой только при одновременном выполнении **четырёх** условий:

```
source_type       === "legal_act"
relevance_status  === "direct"
content_checked   === true
search_confirmed  === true
```

плюс совпадение названия акта источника с названием нормы. Реализация — `confirmsLegalNorm()` и `linkApplicableLawsToSources()` в `lib/confirm-sources-with-search.ts`. Это единственная точка во всей системе, где рождается `source_confirmed`.

### 7.3 Устранённое противоречие (завершено)

**Дефект.** Языковая модель обязана вернуть `verification_status` для каждой применимой нормы, и это значение принималось парсером как есть — при том, что у `ApplicableLaw` вообще нет поля URL и сверять статус было не с чем. Серверная проверка затем устанавливала `source_confirmed: false`, но модельное `"official"` переносилось в итоговый объект нетронутым. Возникало состояние:

```
verification_status: "official"  +  source_confirmed: false  +  source_article: absent
```

**Исправление.** В `linkApplicableLawsToSources()` добавлена односторонняя нормализация:

```ts
if (sourceConfirmed)                  return verificationStatus;  // не повышаем
if (verificationStatus === "official") return "unverified";       // понижаем
return verificationStatus;                                        // not_found / undefined как есть
```

Правила итоговой модели статусов:

| Состояние | `verification_status` | `source_confirmed` | `source_article` |
|---|---|---|---|
| Подтверждённый официальный источник | `official` | `true` | разрешён |
| Официальный на вид, но не подтверждённый | `unverified` | `false` | запрещён |
| Рекомендация / шаблон | `unverified` | `false` | запрещён |
| Неизвестно / не проверено | `not_found` или отсутствует | `false` | запрещён |

Свойства: понижение **одностороннее** (`not_found` никогда не повышается до `unverified`); отсутствующий статус не создаётся искусственно; нормализация питается тем же флагом `sourceConfirmed`, что и `source_confirmed` с `source_article`, поэтому рассинхронизация трёх полей невозможна по построению.

### 7.4 Инвариант `source_article`

`source_article` — это статья, извлечённая из **реально загруженного текста** официальной страницы (`parse-adilet-articles.ts` → `findAdiletArticle`), а не из ответа модели. Защита двойная:

1. поля нет в типе `RawApplicableLaw`, поэтому модель не может его инъецировать через парсер;
2. любое ранее существовавшее значение вырезается в обеих ветках `linkApplicableLawsToSources` и восстанавливается только при `sourceConfirmed === true`.

### 7.5 Изоляция retrieval

Retrieval не создаёт полей верификации. Подтверждено тестами: `retrieval_score` равный 1 не подтверждает источник; `article_number` из retrieval не создаёт подтверждённый `source_article`; отказ retrieval ничего не подтверждает в ответе. Все тесты изоляции зелёные.

## 8. Benchmark methodology

- **Задача**: по пользовательскому запросу найти правильную статью правильного акта.
- **Кейсов**: **20**, реальные пользовательские формулировки.
- **Baseline**: чистый семантический поиск по косинусной близости.
- **Hybrid**: тот же поиск + переранжирование (α = 0.15, boost = 0.05) по пулу из 50 кандидатов.
- **Метрики**: Recall@k для k ∈ {1, 3, 5, 10, 20, 30, 50}; ранг правильной статьи (mean, median, max).
- Коэффициенты подобраны в эксперименте Colab; отчёт — `data/benchmarks/zankomek_rag_benchmark_20_report.json`.

Ограничение методики фиксируется явно: 20 кейсов — небольшая выборка, доверительные интервалы не вычислялись, коэффициенты являются отправной точкой, а не итоговой продовой конфигурацией.

### 9.4 Интерпретация

Гибрид улучшает все метрики Recall и заметно сокращает ранг: медиана падает с 7 до 3.5, худший случай — с 47 до 23. Практический смысл: при Top-K = 5 доля попаданий растёт с 0.40 до 0.60.

**Регрессии не скрываются**: в 3 случаях из 20 ранг ухудшился. Причина в природе лексических сигналов — бонус за предсказанный акт и пересечение заголовков помогают, когда заголовок статьи лексически близок к запросу, и мешают, когда правильная статья названа абстрактно, а конкурент из того же акта имеет более «похожий» заголовок. Чистого выигрыша во всех случаях гибрид не даёт и не заявляется как дающий.

Baseline Law Recall@1 = 0.90 показывает, что определение **акта** решается почти всегда; узкое место — выбор **конкретной статьи** внутри акта.

## 10. Performance

### 10.1 Измеренная стоимость этапов

Замеры выполнены на реальном артефакте, 5 последовательных прогонов на локальный этап.

| Этап | first | median | min | max |
|---|---|---|---|---|
| `fs.readFile` (61.5 MiB, utf8) | 179.7 ms | **116.7 ms** | 116.0 ms | 179.7 ms |
| `JSON.parse` | 214.8 ms | **189.5 ms** | 174.8 ms | 214.8 ms |
| Парсинг + валидация | 229.8 ms | **194.1 ms** | 190.1 ms | 229.8 ms |
| **Production reader целиком** | 372.1 ms | **373.6 ms** | 341.0 ms | 403.6 ms |
| Semantic search (2002 записи, Top-50) | 14.3 ms | **5.7 ms** | 4.6 ms | 14.3 ms |
| Hybrid rerank (пул 50) | 1.8 ms | **0.6 ms** | 0.6 ms | 1.8 ms |
| Query embedding (сеть, 3 запроса) | 19 122 ms | **6 029 ms** | 1 749 ms | 19 122 ms |

Валидация всех 3 075 072 значений векторов добавляет к разбору лишь ≈ 4.6 ms — оптимизировать там нечего.

### 10.2 Память

| Состояние | RSS | heapUsed |
|---|---|---|
| до загрузки | 73.4 MB | 7.3 MB |
| один артефакт резидентно | 189.2 MB | 36.8 MB |
| **прирост** | **+115.8 MB** | +29.5 MB |

≈ 10.1 байта на хранимое число — согласуется с представлением массивов чисел в V8. Файл на диске 64.5 MB, но цена постоянного кэша в памяти — **≈ +116 MB RSS**.

### 10.3 Что было изменено

**До оптимизации.** `retrieveLegalContext()` на каждый вызов создавал новый retriever, который заново читал и разбирал артефакт. Помимо ~374 ms на запрос, это создавало риск: несколько одновременных запросов на холодном старте могли параллельно разбирать по своей копии в 61.5 MiB.

**После оптимизации** (два уровня, оба минимальные):

1. внутри экземпляра retriever кэшируется **promise** загрузки — параллельные первые вызовы разделяют одно чтение, а не запускают несколько;
2. на уровне модуля лениво создаётся **один runtime retriever на Node-процесс**, поэтому кэш переживает границу запроса.

Путь к артефакту при этом **не замораживается**: он резолвится из окружения на каждом вызове, а без конфигурации retrieval возвращает пустой контекст и не создаёт OpenAI-клиент.

Что по-прежнему выполняется **на каждый запрос**: query embedding, semantic search, hybrid reranking, вся верификация. Кэшируется только иммутабельный артефакт.

### 10.4 Честная оценка эффекта

Кэш устраняет ~374 ms — это **98.3 % локальной процессорной работы** слоя retrieval, но лишь **≈ 5.8 %** времени одного retrieval-запроса с учётом сети и доли процента от полного времени `/api/analyze`.

**Полная acceptance latency осталась в диапазоне 105–128 секунд.** Основное время приходится на внешние сетевые этапы: вызов языковой модели, поиск Tavily, загрузка страниц Adilet. Утверждать, что этот кэш радикально ускорил API, было бы неверно — его реальная ценность в предсказуемости и в снятии риска параллельных разборов артефакта.

## 12. Known limitations

Ограничения зафиксированы намеренно и **не исправлялись** на этапе закрытия.

1. **`source_url` у части неподтверждённых норм ведёт не туда.** Все 15 неподтверждённых норм несут `source_url`; в отдельных случаях он указывает на другой документ или на служебную подстраницу (`/links`, `/info`) вместо текста акта. Интерфейс показывает ссылку рядом с бейджем «Не подтверждено».
2. **`primary_legal_act` иногда определяется неверно** — в одном из шести кейсов для вопроса о проверке госоргана был выбран закон о персональных данных. В 5 из 6 кейсов поле `found` равно `false` при наличии `official_url`.
3. **Низкая доля полной Adilet content verification.** Источники проходят поиск и проверку домена, но загрузка и разбор текста доходят до конца редко (`content_checked: false`), поэтому 5 из 6 кейсов завершились статусом `unverified`.
4. **Модель иногда объединяет несколько статей в одно поле** `article` (например, «ст. 85-2, ст. 131, ст. 322») — постатейная верификация такой строки невозможна по построению.
5. **Латентность 105–128 секунд** слишком высока для идеального интерактивного UX; без стриминга и индикации прогресса ожидание ощущается как зависание.
6. **Runtime-кэш артефакта улучшает локальную работу, но почти не влияет на полную латентность** (≈ 374 ms при общем времени ≈ 116 с).

> **Существенно: ни одно из перечисленных ограничений не нарушает verification invariant, потому что неподтверждённые нормы не выдаются как подтверждённые.** Они влияют на полноту и на аккуратность выдачи, но не на достоверность статуса: `source_confirmed` остаётся честным, `source_article` не появляется без подтверждения, а `legal_information_status` и `search_notice` открыто сообщают пользователю, что прямой текст нормы не подтверждён.

## 13. Что считается подтверждённым источником

Источник считается подтверждённым, только если **одновременно**:

1. домен принадлежит списку официальных (7 доменов);
2. URL найден серверным поиском — `search_confirmed: true`;
3. страница действительно загружена и её текст разобран — `content_checked: true`;
4. содержательная релевантность — `relevance_status: "direct"`;
5. тип источника — `source_type: "legal_act"`;
6. название акта источника совпадает с названием нормы.

Только при выполнении всех шести условий появляются `source_confirmed: true`, разрешается `source_article` и сохраняется `verification_status: "official"`.

Что подтверждением **не является**: официальность одного лишь домена; попадание URL в результаты поиска без загрузки текста; `official_guidance` и `official_authority` (подтверждают позицию или компетенцию органа, но не текст закона); `secondary_analysis` (юридическая аналитика); документ «О внесении изменений и дополнений…», если он не содержит требуемую норму.

Пользователю ограничения проверки сообщаются прямо: сервер проверяет домен, совпадение URL с результатами поиска и релевантность извлечённого текста, но **актуальность редакции нормы, точное соответствие статьи и полнота документа автоматически не гарантируются**.

---

## 14. Что RAG не имеет права подтверждать

Ни retrieval, ни reranking, ни языковая модель не могут:

- устанавливать или изменять `source_confirmed`;
- создавать `source_article`;
- устанавливать `search_confirmed` или `content_checked`;
- повышать `verification_status` до `official`;
- влиять на `legal_information_status` или `verified_by_search`.

Высокий `retrieval_score` — включая 1.0 — означает только семантическую близость. `article_number` из записи артефакта — это метаданные корпуса, а не подтверждение того, что норма применима и действует в актуальной редакции.

В клиентский JSON не попадают: векторы эмбеддингов, `retrieval_score`, `chunk_text`, `chunk_id`, `chunk_index`, `chunk_total`, внутренний retrieval-контекст. Проверено на всех шести ответах приёмки — совпадений ноль.

Модельный `verification_status` трактуется как подсказка, а не как факт: сервер может только понизить его, но никогда не повысить.

### Замечания по эксплуатации

- Приложение работает в **Node.js runtime** (не Edge): используется `node:fs/promises`, маршрут не помечен как edge.
- Кэш артефакта живёт в процессе. В долгоживущем процессе (VPS, контейнер) эффект полный. В serverless каждый холодный старт платит ~374 ms заново, а каждый параллельный инстанс держит свою копию (**+116 MB RSS**); при лимите функции 512 MB это рискованно, при 1024 MB запас невелик.
- Артефакт в 64.5 MB должен попасть в поставку функции — для serverless потребуется явно включить его в трассировку файлов.
- Без `LEGAL_EMBEDDING_ARTIFACT_PATH` приложение работает штатно: retrieval отключается, запросы к эмбеддингам не отправляются.

## 18. Материал для раздела «Экспериментальная оценка»

### 18.1 Постановка эксперимента

Проверялась гипотеза: **добавление лексических сигналов к плотному семантическому поиску улучшает точность выбора конкретной статьи в русскоязычном юридическом корпусе.**

- Объект: корпус из 7 нормативных актов РК, 1999 статей, 2002 векторных записи (`text-embedding-3-small`, 1536).
- Выборка: 20 реальных пользовательских запросов.
- Условие A (контроль): плотный поиск по косинусной близости.
- Условие B (гибрид): то же + переранжирование пула из 50 (α = 0.15 за пересечение заголовков, +0.05 за предсказанный акт).
- Зависимые переменные: Recall@k, ранг правильной статьи.

### 18.2 Результат

Гибрид улучшил все метрики Recall и сократил ранг правильной статьи: mean 9.60 → 5.90, median 7 → 3.5, max 47 → 23. На рабочей отсечке Top-5 точность выросла с 0.40 до 0.60 (+50 % относительно). Гибрид улучшил ранг в 12 случаях из 20, ухудшил в 3, не изменил в 5.

### 18.3 Обсуждение

Разрыв между Law Recall@1 = 0.90 и Article Recall@1 = 0.30 у базовой конфигурации показывает, что **определение акта и определение статьи — задачи разной трудности**. Эмбеддинги хорошо улавливают тематическую область, но внутри одного кодекса десятки статей близки лексически и семантически, и плотный вектор их плохо различает. Лексический сигнал по заголовку статьи вносит именно ту различающую информацию, которой не хватает.

Три регрессии не случайны и объяснимы: бонус за пересечение заголовков помогает, когда правильная статья названа содержательно, и вредит, когда она названа абстрактно, а конкурент из того же акта имеет более «похожий» заголовок. Это цена лексического сигнала, а не дефект реализации.

### 18.4 Ограничения эксперимента

Выборка из 20 кейсов мала; доверительные интервалы не вычислялись, статистическая значимость не проверялась. Коэффициенты подобраны на той же выборке, на которой измерялся эффект, — отдельного проверочного набора нет, поэтому существует риск переобучения под эти 20 кейсов. Результаты следует читать как измеренную на пилотной выборке отправную точку, а не как окончательную продовую конфигурацию.

### 18.5 Отдельный инженерный результат

Помимо качества поиска, экспериментально измерена стоимость слоя retrieval: загрузка и разбор артефакта 64.5 MB — 374 ms, поиск по 2002 записям — 5.7 ms, переранжирование — 0.6 ms, сетевой вызов эмбеддинга — медиана 6.0 с. Измерение **опровергло исходную гипотезу** о том, что перезагрузка артефакта является основной причиной задержки: её доля составляет ≈ 5.8 % времени retrieval и доли процента полного запроса. Это самостоятельный методический результат — оптимизация была направлена по результатам измерения, а не по интуиции.

## 19. Краткие выводы для демонстрации

1. **Продукт решает реальную задачу**: правовой анализ ситуации по законодательству РК в шести областях права, все шесть сценариев отрабатывают успешно.
2. **Главная инженерная идея — разделение релевантности и подтверждения.** Поиск может ошибаться; подтверждение — нет. Retrieval и reranking физически лишены возможности установить юридическое подтверждение; это делает только сервер по шести жёстким условиям.
3. **Система честна в неопределённости.** Если статья не подтверждена, она так и помечается: «Точная статья требует проверки в официальной базе», статус `unverified`, отдельное уведомление пользователю. Из 17 проверенных норм ноль ложных подтверждений.
4. **Показательный кейс.** На заведомо слишком широкое утверждение о «возврате любого товара за 30 дней» система нашла и полностью верифицировала нужный закон, но подтвердить само утверждение отказалась и разложила ответ на общее правило, исключения и условия.
5. **RAG измерен, а не заявлен.** Гибридное переранжирование улучшило медианный ранг правильной статьи с 7 до 3.5 и Recall@5 с 0.40 до 0.60 — на 20 кейсах, с открытым указанием трёх регрессий.
6. **Оптимизация опиралась на измерение.** Профилирование показало, что узкое место — сеть, а не чтение артефакта; экономия 374 ms зафиксирована честно как малая доля от общего времени в 105–128 с.
7. **Ограничения названы прямо** и не скрыты: неточные `source_url` у неподтверждённых норм, ненадёжный выбор основного акта, низкая доля полной проверки текста Adilet, высокая латентность. Ни одно из них не нарушает достоверность статусов.
8. **Качество зафиксировано тестами**: 107 локальных тестов, все зелёные, включая отдельный набор на изоляцию RAG от верификации.
